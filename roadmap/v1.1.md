# Plan: rocket 1.1 — encrypted transfers and resume

## 1. Context & scope

rocket 1.0 signs every offer, but file bytes cross the LAN in clear text, and a
dropped connection throws the whole transfer away. 1.1 adds:

- **Transfer encryption** between rocket apps (desktop and Android): per-transfer
  ephemeral X25519 keys, agreed inside the signed offer and a newly signed reply,
  and an authenticated, chunked ChaCha20-Poly1305 stream for the body.
- **Resume**: interrupted transfers keep their partial data on the receiver for
  24 hours; the sender retries automatically and offers a Resume button, and
  only the missing bytes are sent.

Out of scope: the browser drop page (browsers allow WebCrypto only in secure
contexts, and the page is plain HTTP; it stays unencrypted and without resume,
and the docs and site say so), HTTPS/TLS, encrypting offer metadata, MCP tool
changes beyond reporting `encrypted` and the retry status.

## 2. Locked decisions

1. **Protocol 2 only.** 1.1 speaks protocol 2 and refuses protocol 1 in both
   directions with a clear "update rocket" message. Peers that advertise
   protocol 1 (or nothing) show as "Needs update" and can't be picked. No
   plaintext fallback, no setting.
2. **Crypto is stdlib + x/crypto only**: `crypto/ecdh` (X25519), `crypto/hkdf`
   (SHA-256), `golang.org/x/crypto/chacha20poly1305`, the existing ed25519 keys.
   No custom primitives, no new key files: identity stays the ed25519 key.
3. **Resume is automatic after an accepted transfer breaks for a network
   reason**: up to 5 sender retries with backoff, then a Resume button. A resume
   of a transfer the person already accepted needs no new approval. Cancel (by
   either side) or decline never leaves resumable state.
4. Release as **v1.1.0** (desktop zips + signed APK, versionCode 2), site and
   docs updated to describe exactly what is and isn't encrypted.

## 3. Architecture & module layout

- `internal/protocol`: v2 offer/reply types, signing bytes, `Proto = 2`.
- `internal/protocol/securestream` (new): key derivation and the framed AEAD
  stream (`NewWriter(w, key)`, `NewReader(r, key)`), fuzz + vector tests.
- `internal/transfer`: v2 body (see §4.4) replacing tar for peer transfers,
  resume-point verification on the sender, retry loop with backoff.
- `internal/receiver`: decrypting receive path, resume store
  (`<data-dir>/resume/<transfer>.json` + the kept partial files), expiry sweep,
  auto-accept of resumes.
- `internal/discovery`: beacon gains `"proto":2`; mDNS TXT `proto=2`; registry
  exposes `proto` per peer (missing = 1).
- `internal/httpapi` + `web/`: lock badge "Encrypted", "Needs update" peers,
  "Reconnecting (n/5)" state, History "Interrupted" with Resume / Discard,
  receiver-side list of kept partials with Discard.
- `mobile/rocketcore` + `android/`: same features through the Go core; Kotlin UI
  for badges, Needs update, Reconnecting, Resume/Discard.
- Drop page code paths keep their 1.0 behaviour (multipart, plain HTTP).

## 4. Interfaces & contracts

### 4.1 Hello
`{"proto":2, ...}` unchanged otherwise. Sender requires `proto == 2`; on 1 it
fails with `"<name> runs an older rocket (protocol 1); update it to 1.1 or
later"`.

### 4.2 Offer (POST /api/offer)
Adds `"eph": "<base64 X25519 public key, 32 bytes>"` (fresh per offer). Signing
bytes:

```
"rocket-offer-v2\n" + receiver_fp + "\n" + sender_fp + "\n" + ts + "\n" + nonce + "\n" + eph + "\n" + hex(sha256(canonical manifest JSON))
```

A receiver answers a `proto:1` offer with **426** and body
`"this device runs rocket 1.1 or later; update the sender"`.

### 4.3 Reply
Every reply (accepted or not) is signed by the receiver's ed25519 key:

```json
{"accepted":true,"transfer_id":"…","token":"…","eph":"<b64 X25519>","resume":{"entry":3,"offset":1048576,"sha256":"<hex>"},"sig":"<b64>"}
```

`resume` is present only when resumable state exists. Signing bytes:

```
"rocket-reply-v2\n" + hex(sha256(offer signing bytes)) + "\n" + accepted("1"|"0") + "\n" + transfer_id + "\n" + token + "\n" + eph + "\n" + reason + "\n" + resumeField
```

`resumeField` is `entry:offset:sha256` or `-`. The sender verifies the
signature with the `pub` from hello (whose fingerprint already matched the
target) and refuses unsigned or bad replies.

### 4.4 Key and body
- `shared = X25519(own eph private, peer eph public)`; reject the all-zero result.
- `key = HKDF-SHA256(ikm=shared, salt=sha256(offer signing bytes), info="rocket-v2 body\n"+sender_fp+"\n"+receiver_fp+"\n"+transfer_id)`, 32 bytes.
- Plaintext body = a 16-byte start header (`entry` uint32 BE, `offset` uint64 BE,
  4 zero bytes) followed by the bytes of every file in manifest order starting
  at (`entry`, `offset`); folders contribute nothing. No tar: the signed
  manifest already fixes names, order and sizes.
- Framing (`securestream`): frames of `uint32 BE ciphertext length` +
  ChaCha20-Poly1305 ciphertext of up to 64 KiB plaintext. Nonce = 8-byte BE
  frame counter ‖ 3 zero bytes ‖ last-flag byte (1 on the final frame, which may
  be empty). Truncation (EOF without a last frame), data after the last frame, a
  frame over 64 KiB+16, counter overflow or any auth failure is an error that
  aborts and (for auth failure) discards the transfer.
- The header's start point must be either `(0,0)` or exactly the `resume` point
  the receiver offered; anything else is refused. `(0,0)` with a resume offered
  means "start over": the receiver drops the kept partial and writes fresh.

### 4.5 Resume
- Receiver keeps state only for an **accepted peer transfer that failed for a
  network reason** (read error, EOF, timeout, connection reset) — never for
  cancel, decline, auth failure, size/manifest mismatch, or disk errors.
  State: sender fp + pinned-at-time pub, manifest hash, the folder/file
  locations created, entries complete, bytes of the current entry. Kept 24 h,
  swept at start-up and hourly, removed on Discard or completion.
- A new offer from the same sender pub with the same manifest hash and live
  state gets `resume` in the reply and is **auto-accepted** without a prompt.
  `sha256` covers bytes `[0, offset)` of entry `entry`.
- The sender hashes the same prefix of its local file; on match it starts at the
  resume point, otherwise at `(0,0)`. Files already complete are trusted as-is
  (sizes match the manifest; content was authenticated when it was received).
- Sender retry: on a network-class failure after acceptance, retry with a fresh
  offer (new nonce and eph) after 2, 5, 10, 20, 30 s; UI state "Reconnecting
  (n/5)". After the last attempt the history entry is `interrupted` and gets a
  Resume button (desktop keeps the source paths in `<data-dir>/outgoing/`;
  Android keeps the URIs, taking persistable permission where the provider
  allows, else Resume asks to pick the files again).
- History gains `result: "interrupted"`, and every peer entry records
  `encrypted: true`.

### 4.6 UI and accessibility
Same rules as 1.0: status is icon + word ("Encrypted", "Needs update",
"Reconnecting 2/5", "Interrupted"), keyboard reachable, screen-reader labels,
200% font scale on Android, light and dark.

## 5. Risks

1. **Crypto misuse** (nonce reuse, unauthenticated final frame, key reuse across
   transfers): fresh eph keys per offer, counter nonces with last flag, transfer
   id in HKDF info, known-answer and tamper/truncate/reorder tests, a fuzz test
   on the reader, and an independent review stage focused on crypto.
2. **Resume integrity** (source changed, wrong offset, attacker-chosen offset):
   prefix hash check, start point limited to (0,0) or the receiver's own
   offer, resume bound to sender pub + manifest hash, all inside signed messages.
3. **Disk leaks from kept partials**: 24 h expiry, sweep, visible Discard,
   cancel/decline never keep state.
4. **Protocol-1 peers breaking silently**: explicit refusal messages both ways,
   "Needs update" in peer lists, CHANGELOG/README/site call it out.
5. **Go toolchain drift**: tests currently fail under Go 1.27 (transfers
   reported "cancelled by the receiver"). Fix that first so tests pass on 1.26
   and 1.27; CI adds 1.27 to the matrix.
